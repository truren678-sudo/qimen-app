# 九宮奇門命盤用戶版 App 規劃

版本：v0.1  
日期：2026-05-04  
定位：從現有命理師自用排盤工具中提取「命盤」能力，重新設計成面向一般用戶的獨立 App。

## 1. 產品方向

### 1.1 核心判斷

現有 `qimen-app` 已具備命盤排盤能力，但目前產品形態偏命理師自用：

- 功能入口以「排盤系統」為中心。
- 畫面直接呈現專業盤面與術語。
- 用戶需要懂奇門符號才能理解結果。

新的用戶版 App 不應直接搬運現有 UI，而應改成：

> 讓一般用戶輸入出生資料後，看懂自己的九宮奇門命盤、人生主題、大限節奏與可行建議。

### 1.2 FateTell 對標方式

FateTell 可作為產品成熟度對標，但不應抄它的視覺、文案與互動細節。

可學習的方向：

- 東方命理不以工具方式呈現，而以日常陪伴與自我理解呈現。
- 先給白話摘要，再讓用戶逐步深入專業細節。
- 用 AI 問答承接用戶的具體問題。
- 用每日、年度、主題報告提高回訪與付費轉化。

我們的差異化：

- FateTell 偏八字、易經、AI companion。
- 本產品偏九宮奇門命盤、十二人事宮、大限流年、轉太極論命。
- 產品主張不是泛泛算命，而是「人生結構地圖 + 時間節奏導航」。

建議定位語：

> 九宮奇門命盤，讀懂你的人生結構與階段節奏。

## 2. 目標用戶

### 2.1 第一目標用戶

對命理、自我理解、人生方向感有需求，但不懂專業術語的一般用戶。

常見問題：

- 我適合什麼樣的工作？
- 我的感情模式是什麼？
- 我現在這十年應該把重點放在哪裡？
- 今年適合主動出擊，還是保守累積？
- 我的財運、事業、關係哪裡強，哪裡容易卡？

### 2.2 第二目標用戶

已經接觸過八字、紫微、占星、塔羅等工具，願意嘗試新的東方命理系統的人。

這類用戶需要：

- 專業感
- 系統感
- 可驗證的個人化結果
- 與現有命理 App 不同的分析視角

### 2.3 不服務或需轉介的場景

App 不應承接以下高風險需求：

- 醫療診斷
- 法律決策
- 投資保證
- 恐嚇式化解
- 絕對化預言
- 心理危機處理

這些場景應以合規提示、風險聲明、轉介專業服務處理。

## 4. 系統分層

新 App 應分為五層。

### 4.1 排盤核心層

來源：現有 `src/qimen.js`

目標 API：

```js
calculateMingPan({
  calendarType,
  birthDate,
  birthTime,
  gender,
  birthLocation,
  isDst,
  useTrueSolarTime
})
```

輸出：

- solar
- lunar
- siZhu
- chartType = `命盤`
- gender
- yinYang
- juNum
- xunShou
- kongWang
- yiMa
- zhiFuXing
- zhiShiMen
- fuYinFanYin
- palaces

### 4.2 命盤事實層

將排盤結果轉成可解讀的 facts。

建議資料結構：

```js
{
  profile: {
    gender,
    birthInput,
    normalizedBirthTime,
    solar,
    lunar,
    siZhu
  },
  chart: {
    yinYang,
    juNum,
    xunShou,
    kongWang,
    yiMa,
    zhiFuXing,
    zhiShiMen,
    fuYinFanYin
  },
  palaces: [
    {
      num,
      name,
      element,
      personnel12,
      daXian,
      liuNianAges,
      shen,
      star,
      door,
      tianGan,
      diGan,
      harms,
      isKong,
      isMa,
      score,
      strength
    }
  ],
  derived: {
    mingGong,
    shenGong,
    platformGong,
    careerPalace,
    wealthPalace,
    spousePalace,
    currentDaXian,
    currentYearPalace
  }
}
```

這層很關鍵，因為 AI 不應直接讀 UI 狀態，而應讀乾淨的命盤事實。

### 4.3 規則判讀層

來源：v7.3 規則庫。

職責：

- 根據 facts 找對應規則。
- 依論命五步驟產出技術判讀。
- 不負責把話說得好聽。

建議第一版先做半結構化規則，不急著把全部規則轉成程式判斷。

優先工程化：

- 十二宮分類：人物宮 / 事件宮
- 四害：入墓 / 擊刑 / 門迫 / 空亡
- 馬星
- 旺衰與幸運指數
- 命財官判定
- 當前大限
- 流年所在宮位

### 4.4 用戶翻譯層

來源：v1.0.1 翻譯器。

職責：

- 將技術判讀轉成用戶可接受語言。
- 控制語氣、分層、行動建議。
- 避免恐嚇、絕對化、過度承諾。

基本輸出規則：

- 先摘要，後細節。
- 先共情，再判讀。
- 指出風險必須給應對方向。
- 禁止「一定」「必然」「注定」「保證」。
- 不做醫療、法律、投資保證。

### 4.5 App 體驗層

職責：

- 使用者輸入
- 命盤結果展示
- 十二宮卡片
- 大限時間線
- AI 問答
- 收藏與報告
- 付費解鎖

這層不應暴露過多技術術語。

## 5. MVP 功能

第一版目標：讓用戶完成一次出生資料輸入，得到可理解、可保存、可分享的命盤解讀。

### 5.1 必做

- 出生資料輸入
- 公曆 / 農曆切換
- 性別
- 出生地
- 夏令時
- 真太陽時修正
- 生成命盤
- 命盤總覽
- 九宮盤面
- 十二人事宮卡片
- 當前大限
- 基礎年度提示
- 本地保存
- 匯出文字報告

### 5.2 可延後

- 帳號系統
- 雲端同步
- 圖片報告
- 伴侶合盤
- 推播
- App Store 內購
- 多語言
- 每日運勢

### 5.3 不建議第一版做

- 完整 AI companion
- 所有主題的完整深度解讀
- 高度自動化付費報告生成
- 太多玄學化化解內容

第一版先證明：用戶能輸入、生盤、看懂、保存、願意回來。

## 6. 頁面資訊架構

### 6.1 Onboarding

目的：建立信任，不炫技。

內容：

- App 是什麼
- 命盤能看什麼
- 命理僅作參考
- 隱私與出生資料說明

### 6.2 出生資料頁

欄位：

- 姓名或暱稱
- 性別
- 公曆 / 農曆
- 出生年月日
- 出生時間
- 出生地
- 是否夏令時
- 是否使用真太陽時

設計要求：

- 預設簡潔。
- 進階設定可折疊。
- 出生地修正要用生活語言解釋，不用一開始丟「真太陽時」術語。

### 6.3 命盤首頁

內容優先級：

1. 一句命盤核心摘要
2. 目前人生階段
3. 三個強項宮位
4. 三個需留意宮位
5. 進入完整九宮盤

### 6.4 九宮盤頁

保留專業盤面，但要加分層：

- 預設展示簡化九宮
- 點宮位後看詳情
- 可切換專業模式
- 專業模式才顯示完整神星門干與四害標記

### 6.5 十二宮頁

十二張主題卡：

- 命宮
- 兄弟
- 夫妻
- 子女
- 財帛
- 疾厄
- 遷移
- 交友
- 事業
- 田宅
- 福德
- 父母

每張卡包含：

- 主題摘要
- 目前狀態
- 優勢
- 風險
- 行動建議
- 專業依據可展開

### 6.6 大限時間線

內容：

- 每十年一段
- 標示當前大限
- 顯示該階段核心課題
- 顯示機會點與挑戰點

### 6.7 AI 問答

第一版可以做成主題問答，而不是自由聊天。

建議預設問題：

- 我適合什麼工作？
- 我的感情模式是什麼？
- 這十年事業該怎麼走？
- 我今年需要注意什麼？
- 我的財運強項在哪裡？

回答必須引用 facts + v7.3 規則，不得脫離命盤亂聊。

## 7. 解讀輸出格式

### 7.1 命盤總覽

```txt
你的命盤整體呈現出 ______ 的結構。

最明顯的優勢在 ______，代表你在 ______ 方面較容易建立成果。
需要留意的是 ______，這不代表不好，而是這些領域需要更有策略地經營。

你目前走在 ______ 大限，這個階段的主題是 ______。
```

### 7.2 單宮卡片

```txt
【事業宮】

一句話摘要：
你在事業上比較適合 ______。

優勢：
______

需要留意：
______

行動建議：
______

專業依據：
本宮位落 ______，見 ______，四害狀態為 ______。
```

### 7.3 大限卡片

```txt
【31-40 歲大限】

這十年的核心課題是 ______。

比較容易得到支持的領域：
______

需要主動處理的挑戰：
______

建議：
______
```

### 8.2 也可先在現有 repo 開 `apps/mingpan-user`

如果想共用現有核心但保持隔離，可做成：

```txt
qimen-app/
  apps/
```

### 8.3 內容工程化順序

1. 從現有 `qimen.js` 包出 `calculateMingPan`
2. 抽出時間修正邏輯
3. 建立 facts builder
4. 將 v7.3 拆章節成 Markdown 或 JSON
5. 寫第一批 deterministic interpreters
6. 再接 AI 生成用戶語言

## 9. 風險與注意事項

### 9.1 算法風險

出生時間、時區、真太陽時、農曆轉換是最高風險。

必須建立測試案例：

- 公曆生日
- 農曆生日
- 閏月
- 晚子時
- 海外出生
- 夏令時
- 真太陽時修正跨時辰

### 9.2 解讀風險

AI 可能過度發揮。

需要：

- 明確 prompt policy
- 禁止跨系統引用
- 禁止絕對化
- 禁止醫療、法律、投資保證
- 回答必須基於命盤 facts

### 9.3 產品風險

如果一開始展示太多專業符號，用戶會看不懂。

因此：

- 首頁不直接丟完整命盤。
- 專業盤面放第二層。
- 用戶語言優先，術語可展開。

## 11. 建議第一個開發 Sprint

Sprint 1 目標：不追求漂亮，先跑通「生盤 -> facts -> 白話摘要」。

任務：

- 建立新 App 專案
- 搬入命盤核心
- 搬入 location data
- 完成出生資料表單
- 生成命盤 facts
- 顯示命盤總覽
- 顯示九宮盤
- 寫 3 個固定模板解讀

完成標準：

- 用戶輸入出生資料後能生成命盤。
- 命盤結果與現有工具一致。
- 至少能輸出一段普通用戶看得懂的總覽解讀。
